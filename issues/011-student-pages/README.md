## 목표

학생이 화면에서 자습실을 골라 방문을 신청하고, 시간을 바꾸거나 취소하며, 자기 신청 상태를 한눈에 확인한다. 과제 발문의 세 가지 불만을 화면에서 해결한다.

| 발문의 불만 | 해결 |
|---|---|
| "신청은 했는데 제가 명단에 있는 건지 모르겠어요" | 자습실 목록에 **내 상태**(신청함·방문함 등), 내 신청에 예정·지난·취소 묶음과 **누가 왜 취소했는지** |
| "7시에 가기로 했는데 8시로 바꾸려면 누구한테 말해요?" | 내 신청에서 **직접 시간 변경** |
| "자습실 열 때마다 공지 올리고 인원 세는 게 일이에요" (강사) | 학생이 직접 신청하고 정원은 서버가 지킴, 정원이 차면 "정원 마감" |

## 범위

- 포함
  - 자습실 `/student/rooms`: 자습실별 내 상태·행동(신청, 다시 신청, 신청함, 방문함, 정원 마감, 운영 종료), 방문 시각 선택 신청
  - 내 신청 `/student/visits`: 예정·지난 방문·취소됨 묶음, 시간 변경, 취소(사유 선택), 취소 주체·사유
  - `VisitTimeDialog`(신청·시간 변경 공용), `CancelVisitDialog`를 사유 필수/선택 설정으로 공용화
  - 헤더 학생 메뉴

## 결정 기록 (Decision Log)

| 날짜 | 결정 | 이유 / 검토한 대안 |
|---|---|---|
| 2026-11-16 | **`staleTime` 30초 → 0 (브라우저 확인에서 발견한 문제 수정)** | 강사가 학생 신청을 취소한 뒤 학생이 "내 신청"으로 이동해도 30초 동안 "예정"으로 보였다. 자습실 목록도 내 신청 데이터를 쓰므로 방금 받아 둔 데이터를 "최신"으로 간주했기 때문이다. 화면에 무엇이 보이는지 먼저 확인해 원인을 확정한 뒤 고쳤다. 여러 사람이 같은 데이터를 바꾸는 서비스이고, "명단에 있는지" 확인하는 화면이 옛 상태를 보여주면 목적이 무너진다. 응답이 작은 조회라 요청 증가 비용은 작다. |
| 2026-11-16 | **취소 주체 문구를 주체별로 정함** | 처음에는 `${라벨}이(가)`처럼 조사를 기계적으로 붙여 "강사이(가) 취소했습니다"가 나왔다. 사용자에게 보이는 문장이므로 주체별 문장(`내가 / 강사가 / 자동으로`)을 `Record`로 정했다. |
| 2026-11-16 | **자습실 목록에 내 상태를 함께 표시** | 학생이 "내가 이 자습실에 신청했나?"를 확인하려고 화면을 오가지 않게 한다. 내 신청이 있으면 정원 마감보다 우선 보여준다 (정원 안에 내 신청이 포함되어 있으므로). |
| 2026-11-16 | **취소한 자습실은 "다시 신청"으로 표시** | 서버는 같은 신청을 재활성화한다(R3). 화면도 새 신청이 아니라 다시 신청임을 알려준다. |
| 2026-11-16 | **신청·시간 변경이 같은 시각 선택 대화상자를 씀** | 둘 다 "운영 기간 안, 지금 이후의 시각"을 고르는 같은 입력이다. 시간 변경은 기존 시각을 미리 채운다. |
| 2026-11-16 | **취소 대화상자를 사유 필수/선택 설정으로 공용화** | 강사(필수)와 학생(선택)의 차이는 그 하나다. 두 벌로 두면 사유 처리 규칙(공백 제거)이 어긋날 수 있다. |
| 2026-11-16 | **입력칸의 min/max는 안내일 뿐** | 브라우저가 min/max를 강제하지 않는 경우가 있다. 제출 전 `validateVisitTime`이 다시 검사하고, 최종 판단은 서버다. |
| 2026-11-16 | **화면 시각 고정은 `vi.setSystemTime`** | `useNow`가 `Date.now()`를 읽으므로 컴포넌트 테스트에서 시각을 고정해 "지난 시각 막기"를 결정적으로 검증한다. |
