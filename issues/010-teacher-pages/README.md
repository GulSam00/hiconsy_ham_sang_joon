## 목표

강사가 화면에서 자습실을 열고 관리하며, 신청 현황과 이력을 확인한다. 특히 수정이 기존 신청과 충돌할 때(R6, R7) 강사가 막히지 않고 **신청을 골라 사유와 함께 취소한 뒤 다시 저장**하는 흐름을 화면에서 완성한다.

## 범위

- 포함
  - 자습실 목록 `/teacher/rooms`: 운영 상태(예정·운영 중·종료), 기간(KST), 신청 수/정원 막대, 새 자습실 등록
  - 자습실 상세 `/teacher/rooms/:id`: 수정(바뀐 값만 전송), **충돌 안내 + 강사 취소 + 다시 저장**, 삭제(자동 취소될 예정 신청 수 경고), 신청자 목록(예정 신청 취소), 이력 타임라인
  - 학생 관리 `/teacher/students`: 목록, 등록, 인라인 수정, 삭제(자동 취소 경고)
  - 공통 컴포넌트: `BaseDialog`, `ConfirmDialog`, `CancelVisitDialog`, `RoomForm`, `RoomConflictPanel`, `HistoryTimeline`, `VisitStateBadge`
  - 헤더 역할별 메뉴
- 제외 (다른 이슈로)
  - 학생 화면 → ISSUE-011

## 설계 메모

R6 충돌 해결 흐름 (상세 화면):

```
저장 → updateRoom 409 CAPACITY_BELOW_ACTIVE
  → toRoomConflict(error)            # details 타입 가드
  → withoutVisits(conflict, 취소한 id)  # 에러 객체는 건드리지 않고 걸러 보여줌
  → RoomConflictPanel: [취소] → CancelVisitDialog(사유 필수) → cancelVisit
  → [다시 저장] → 마지막 요청(lastUpdate) 재전송
```

```
apps/web/src/
├── api/        rooms.ts, visits.ts, students.ts(확장)
├── queries/    keys.ts(rooms·students 계층), useRooms.ts, useRoomVisits.ts, useStudents.ts
├── utils/      room-form.ts, student-form.ts, conflicts.ts, labels.ts, room-phase.ts
├── composables/useNow.ts
├── components/ BaseDialog, ConfirmDialog, CancelVisitDialog, RoomForm, RoomConflictPanel, HistoryTimeline, VisitStateBadge
└── pages/teacher/ TeacherRoomsPage, TeacherRoomDetailPage, TeacherStudentsPage
```

## 결정 기록 (Decision Log)

| 날짜 | 결정 | 이유 / 검토한 대안 |
|---|---|---|
| 2026-11-15 | **수정은 바뀐 값만 전송** | 전체를 보내도 서버 결과는 같지만, 충돌이 났을 때 무엇을 바꾸려다 실패했는지가 요청에 드러나고 "다시 저장"도 같은 의도를 그대로 다시 보낸다. 바뀐 값이 없으면 요청 자체를 하지 않는다. |
| 2026-11-15 | **충돌은 폼 에러가 아니라 전용 안내 패널로** | 정원·기간 충돌은 입력이 틀린 게 아니라 다른 데이터(신청)와 부딪힌 것이다. 필드 아래 빨간 글씨로는 해결 방법(신청 취소)을 보여줄 수 없다. |
| 2026-11-15 | **충돌 안내에서 취소한 신청은 화면에서 걸러 표시** | "다시 저장" 전까지 서버에서 충돌 목록을 다시 받지 않는다. 처음에는 에러 객체의 배열을 직접 지웠는데, TanStack Query가 관리하는 객체를 바꾸는 것이라 `withoutVisits()`로 새 값을 만들도록 고쳤다. |
| 2026-11-15 | **삭제 성공 시 캐시를 정교하게 처리 (브라우저 확인에서 발견한 문제 수정)** | 실제 API로 확인하다 삭제 후 목록에 그 자습실이 잠깐 남는 것을 발견했다. 상세 화면에 있는 동안 목록 query가 비활성이라 무효화만으로는 옛 데이터가 먼저 보였다. 목록 캐시에서 즉시 빼고, 삭제한 자습실의 상세 캐시는 제거(무효화하면 404 재요청)하도록 고치고 테스트를 추가했다. |
| 2026-11-15 | **자습실 쓰기는 `rooms` 전체를 무효화** | 신청 취소 하나가 목록의 신청 수, 상세, 신청자, 이력을 모두 바꾼다. 범위를 좁게 추측하다 화면이 어긋나는 것보다 넓게 무효화하는 편이 안전하다. 데이터 양이 작아 비용도 작다. |
| 2026-11-15 | **강사 취소 사유는 서버와 같은 규칙으로 버튼을 막음** | 앞뒤 공백을 지운 값이 비면 버튼을 비활성한다(R11). 서버가 최종 판단하지만, 400을 받기 전에 알려준다. |
| 2026-11-15 | **삭제 확인에 결과를 구체적으로 표시** | "삭제하시겠습니까?"만으로는 학생 신청이 자동 취소된다는 것을 알 수 없다. 예정 신청 수와 "지난 방문은 남는다"를 함께 보여준다 (R8, R9). |
| 2026-11-15 | **운영 상태 배지는 표시 전용** | 화면 시각(`useNow`)으로 계산하지만, 신청 가능 여부 판단은 항상 서버가 한다. 화면 시계가 틀려도 규칙이 깨지지 않는다. |
| 2026-11-15 | **대화상자는 `<dialog>` 대신 직접 구현** | 테스트 환경(happy-dom)의 `<dialog>` 지원이 불완전하다. `role="dialog"`, `aria-modal`, Esc 닫기, 열릴 때 포커스 이동으로 접근성을 지켰다. |
| 2026-11-15 | **브라우저 e2e는 저장소에 넣지 않고 수동 확인 스크립트로** | Playwright 테스트를 저장소에 넣으면 평가자 환경에 브라우저 설치가 필요해 "한 번에 실행" 조건이 무거워진다. 핵심 흐름은 컴포넌트 테스트로 고정하고, 실제 API 연동은 PR마다 브라우저로 확인해 결과를 남긴다. |
