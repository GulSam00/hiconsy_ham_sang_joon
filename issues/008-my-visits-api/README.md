## 목표

학생이 자기 신청과 상태를 한눈에 본다. 과제 발문의 *"신청은 했는데 제가 명단에 있는 건지 모르겠어요"*를 해결하기 위해, 상태뿐 아니라 **취소됐다면 누가 왜 취소했는지**까지 보여준다.

## 범위

- 포함
  - `GET /me/visits` (학생): 신청마다 자습실 요약, 상태, 지난 방문 여부, 취소 정보(주체·사유·시각)
  - 삭제된 자습실의 신청 포함 (`room.isDeleted`)
- 제외 (다른 이슈로)
  - 화면 → ISSUE-011

## 설계 메모

```
GET /me/visits
 ├─ 학생(삭제 안 됨) 확인 ─ 404
 └─ visits WHERE studentId
      include room
      include histories ORDER BY createdAt DESC, id DESC TAKE 1   ← 취소 정보의 원천
```

응답 `cancellation`은 `status = CANCELED`일 때만 마지막 이력에서 만든다. 취소 뒤에는 재신청만 가능하고 재신청하면 ACTIVE가 되므로, CANCELED 상태의 마지막 이력은 항상 취소 이력이다.

## 결정 기록 (Decision Log)

| 날짜 | 결정 | 이유 / 검토한 대안 |
|---|---|---|
| 2026-11-15 | **취소 정보를 응답에 포함** | 상태만 주면 학생은 "왜 취소됐는지" 알 수 없다. 강사·시스템 취소는 학생이 직접 한 일이 아니므로 더욱 그렇다. 별도 API(`/visits/:id/histories`)로 나누면 목록 화면이 신청마다 추가 요청을 해야 한다. |
| 2026-11-15 | **취소 정보는 마지막 이력에서 계산 (비정규화하지 않음)** | `Visit`에 `canceledBy`, `cancelReason`을 두면 이력과 같은 정보를 두 곳에 저장해 어긋날 수 있다. 이력이 원천이고, 응답할 때 읽는다. |
| 2026-11-15 | **N+1 여부를 추측하지 않고 SQL 로그로 확인, 주석 정정** | 처음 주석에 "Prisma가 관계별 take를 일괄 조회로 처리한다"고 썼다. 로그를 보니 쿼리 수는 신청 수와 무관하게 3개로 일정했지만, 관계별 `take: 1`은 SQL이 아니라 메모리에서 적용되어 해당 학생의 이력 전체를 읽었다. 주석을 사실대로 고치고, 이력이 커질 때의 대안(마지막 이력 비정규화)을 적었다. |
| 2026-11-15 | **삭제된 자습실의 신청도 목록에 포함** | 지난 방문은 실제로 일어난 일이고, 시스템 취소는 학생이 이유를 알아야 한다. 대신 `room.isDeleted`로 표시해 화면이 구분할 수 있게 했다. |
| 2026-11-15 | **경로는 `/me/visits`** | CLAUDE.md 8절의 경로 규칙에 이미 예시로 있다. `/students/:id/visits`로 두면 학생이 남의 id를 넣는 경우를 따로 막아야 한다. 요청자 자신의 자원은 `/me`가 의미가 분명하다. |
| 2026-11-15 | **정렬은 방문 시각순 하나, 상태별 묶음은 화면에서** | 예정·지난 방문·취소를 어떻게 묶어 보여줄지는 화면 결정이다. API는 `status`와 `isPast`를 주고, 정렬은 예측 가능한 한 가지로 고정했다. |
